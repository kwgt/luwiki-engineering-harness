# ソースコード検索・解析ガイドライン

リポジトリを調査・解析する際は、ソースファイルを無差別に読み込むのではなく、利用可能なコードインデックスを優先して使用し、必要な箇所だけを段階的に取得すること。

## 基本方針

ソースコードの検索は、原則として次の優先順位で行う。

1. `scip-cli` または `ast-index` を使って対象シンボルや関連箇所を絞り込む
2. 必要に応じて `rg` などのテキスト検索を補助的に使用する
3. 最後に、解析に必要なソースファイルの必要な範囲だけを読む

リポジトリ全体や大きなファイルを、探索目的だけで最初から全文読み込みしないこと。

## scip-cli を優先するケース

対象言語が SCIP インデックスに対応しており、意味的なシンボル解決が必要な場合は `scip-cli` を優先する。

特に以下の調査では `scip-cli` を第一候補とする。

* シンボルの定義位置を特定する
* 特定シンボルへの参照を列挙する
* 同名シンボルを区別する必要がある
* 型情報を考慮して呼び出し先を特定する
* クラスや型のメンバーを調査する
* シンボル間の依存関係・逆依存関係を調査する

単純な文字列一致ではなく、「どの定義を指しているか」が重要な場合は、可能な限り意味解析結果を利用すること。

## ast-index を優先するケース

以下の場合は `ast-index` を優先する。

* SCIP が対象言語を十分にサポートしていない
* Ruby、Scheme など、静的な型解決だけでは参照先を確定しにくい言語を調査する
* リポジトリ全体の構造を広く把握したい
* クラス、関数、メソッド、import、継承などの構造を高速に探索したい
* SCIP で有効な結果が得られなかった
* 正確な意味解決より、関連する候補を幅広く収集することが重要である

`ast-index` の結果は、必ずしも完全な型解決済み参照とは限らない。曖昧性がある場合は周辺コードを確認して判断すること。

## フォールバック戦略

最初から `scip-cli` と `ast-index` の両方を同じ目的で実行しないこと。

まず、言語と検索目的に最も適した一方を利用する。

結果が以下のいずれかに該当する場合のみ、もう一方を追加で利用する。

* 結果が存在しない
* 結果が明らかに不足している
* 複数候補があり曖昧である
* インデックスが対象コードを十分にカバーしていない
* 構文的な候補と意味的な参照の両方を比較する必要がある

原則として次のように判断する。

`静的型付け・SCIP対応・意味解決が重要`
→ `scip-cli`

`動的言語・SCIP未対応・構造探索・候補列挙`
→ `ast-index`

`インデックスで不足`
→ もう一方のインデックス

`文字列・設定・コメント・テンプレートなどを探索`
→ `rg`

`最終確認`
→ 必要なソースコードだけ読む

## rg などのテキスト検索を使うケース

`rg` はコードインデックスを置き換えるものではなく、補助検索として使用する。

以下では `rg` が適している。

* コメント
* エラーメッセージ
* ログ文字列
* 設定値
* SQL
* テンプレート
* ドキュメント
* ファイル名やパス
* 動的に生成されるシンボル名
* インデックスに含まれないコード
* メタプログラミングによる名前の組み立て
* 特定文字列の完全一致検索

関数や型の参照先を調べる目的で、最初から単純な `rg` のみを使わないこと。

## ソースファイルの読み込み

インデックス検索で対象を絞り込んだ後、必要なファイルのみを読む。

可能であれば、ファイル全体ではなく対象シンボルとその周辺範囲だけを取得する。

例えば、あるメソッドの挙動を調べる場合は、

1. メソッドの定義を検索
2. 呼び出し元または依存先を検索
3. 対象メソッド本体を読む
4. 必要になった依存先だけ追加で読む

という順序で進める。

「念のため」という理由だけで多数の関連ファイルを全文読み込みしないこと。

## 呼び出し関係の調査

ある関数やメソッドについて呼び出し関係を調べる場合は、以下の二方向を区別する。

### 呼び出し先を調べる

対象関数が内部で何を利用しているかを調査する。

可能であれば SCIP の依存関係や意味解析済み参照を利用する。

動的言語や意味解決できない呼び出しについては `ast-index` から候補を取得し、必要な箇所だけソースを確認する。

### 呼び出し元を調べる

対象関数を利用しているコードを調査する。

SCIP が正確な参照を提供できる場合は SCIP の参照検索を優先する。

SCIP で解決できない場合は `ast-index` の usage/caller 情報を利用し、それでも不足する場合に `rg` を使う。

## 動的言語の扱い

Ruby、Scheme、および強いメタプログラミングを利用するコードでは、静的解析結果を確定情報として扱わないこと。

以下のような機能が存在する場合、呼び出し関係がインデックスだけでは完全に解決できない可能性を考慮する。

* 動的ディスパッチ
* monkey patch
* method_missing 等の動的呼び出し
* eval
* 動的 require/load
* macro
* 高階関数
* 実行時のクラス・メソッド生成

この場合は、

`ASTによる候補抽出 → 周辺コード確認 → 必要ならテキスト検索`

の順で調査する。

不確実な参照関係を、確定した事実として報告しないこと。

## 調査範囲の拡張

検索結果から新しい依存先が見つかった場合でも、自動的にすべてを追跡しないこと。

現在の質問への回答に必要かを判断し、必要な関係だけ辿る。

例えば、

`Controller → Service → Repository → DB Adapter`

という依存関係があった場合、質問が Service の入力検証についてであれば、DB Adapter まで読む必要がない可能性が高い。

調査の深さは質問に応じて制御すること。

## インデックスの結果を過信しない

`scip-cli` および `ast-index` は探索を効率化するための情報源であり、実際のソースコードより優先される最終的な真実ではない。

以下の場合はソースコードを確認する。

* インデックス結果とコードの内容が矛盾している
* 生成コードが関係している
* インデックスが古い可能性がある
* 条件付きコンパイルや動的ロードが存在する
* 参照先に曖昧性がある
* 実際の実行経路を判断する必要がある

## トークン効率

検索ツールから得られた大量の結果を、そのまま解析コンテキストへ持ち込まないこと。

検索結果が多数ある場合は、

1. ファイル
2. シンボル種別
3. 名前空間・クラス
4. 呼び出し関係
5. 質問との関連性

によって候補をさらに絞り込む。

数百件の候補を読むより、検索条件を追加して数件まで絞ることを優先する。

## 推奨探索フロー

基本的には以下の流れで調査する。

`質問を理解する`

→ `対象言語と対象シンボルを特定する`

→ `SCIP が有効なら scip-cli、そうでなければ ast-index`

→ `候補となる定義・参照・依存関係を取得する`

→ `必要なら別のインデックスで補完する`

→ `必要なら rg で文字列検索する`

→ `最小限のソースコードを読む`

→ `追加調査が必要な関係だけ辿る`

→ `根拠となるコードを確認して回答する`

## 重要原則

コードベースを自力で逐次走査するのではなく、まずインデックスを利用すること。

検索の目的は「関連コードをできるだけ多く集めること」ではなく、「質問に答えるために読む必要があるコードを最小化すること」である。
